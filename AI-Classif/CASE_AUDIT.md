# Аудит соответствия кейсу ТПУ — AI Procurement Copilot

Основание: «Презентация - мероприятие ТПУ.pdf», слайды 3–7. В презентации заданы общий стек, запуск `docker-compose up --build`, отсутствие 504 при обработке файла больше 50 страниц, сценарий семантической классификации и семь критериев приёмки.

## Краткий вывод

В кодовую базу добавлены отсутствовавшие асинхронная обработка PDF/DOCX, хранение статуса задания, выгрузка извлечённого текста, постоянное сохранение обновлённого справочника после перезапуска и проверка PDF на 60 страниц. Интерфейс приведён к чёрно-бело-красной палитре и Times New Roman.

При этом «полностью проходит кейс» можно заявить только после интеграционного запуска на машине участника: в текущей среде нет Docker daemon, PostgreSQL/pgvector, Celery/Redis и загруженной Sentence Transformers модели; npm не смог получить недостающий пакет из registry. Поэтому целевые 85% точности и временные метрики ниже отмечены как требующие реального benchmark, а не как уже доказанные.

## 1. Общие технические требования

| Требование из презентации | Реализация в проекте | Статус проверки |
|---|---|---|
| Frontend: React/Vue/Next, SPA, адаптивность | React + Vite SPA, responsive breakpoints, русскоязычные сценарии | Реализовано в коде; ручной просмотр на физических разрешениях нужен |
| Backend: Python + FastAPI/Django или Node.js | FastAPI REST API, Pydantic validation | Реализовано в коде |
| Очереди: Celery/RabbitMQ/Redis | Celery worker + Redis; batch и ingestion tasks выполняются асинхронно | Реализовано в коде; worker runtime здесь не поднят |
| БД: PostgreSQL | SQLAlchemy модели для каталога, метаданных, истории и документов | Реализовано в коде; интеграционное подключение требует Docker |
| Векторный поиск | pgvector cosine distance + HNSW, Sentence Transformers | Реализовано в коде; реальные поисковые метрики здесь не запускались |

## 2. Развёртывание

| Требование | Что сделано | Статус |
|---|---|---|
| `docker-compose up --build` | Сервисы db, redis, api, worker, web; том `document_uploads` общий у API и worker | Compose-файл проверяется статически; запуск невозможен без Docker daemon |
| README и примеры API | Добавлены инструкции classify, batch, jobs, обновления каталога и загрузки PDF/DOCX | Реализовано |
| Готовый Docker-пакет | Backend и frontend Dockerfile, Nginx proxy, Compose | Docker image build не подтверждён в этой среде |
| Файл более 50 страниц без 504 | API потоково сохраняет upload до 100 МБ и возвращает 202; Celery worker извлекает PDF/DOCX отдельно; лимит worker 30 минут; Nginx upload limit 105 МБ | PDF-тест на 60 страниц проходит локально; end-to-end 504 тест с Docker нужен |
| UX для нетехнических пользователей | Понятный upload, статус очереди, счётчик страниц/символов, скачивание TXT, ошибки на русском | Реализовано в коде |

DOCX не имеет фиксированного числа страниц до отображения в конкретном текстовом редакторе; поэтому для DOCX UI показывает оценку, а для PDF — точное количество страниц. Сканированные PDF без текстового слоя не проходят как будто успешно распознанные: пользователь получает явное сообщение о необходимости OCR. OCR пока не включён.

## 3. Workflow классификатора

| Шаг | Реализация |
|---|---|
| Ввод наименования | Одиночная форма и список до 100 товаров |
| Эмбеддинг | `paraphrase-multilingual-MiniLM-L12-v2`, нормализованные векторы |
| Семантический поиск | pgvector cosine search по локальному каталогу |
| Результат | ОКПД2, приложение, позиция, национальный режим, quota, confidence, альтернативы |
| Ссылка на позицию | Стабильный локальный hash вида `#pp1875-appendix-2-position-199`; открывается третья вкладка и подсвечивает нужную запись |
| Массовая обработка | Лимит 100 товаров, обработка через Celery/Redis, polling статуса |

Внешняя ссылка ведёт на страницу соответствующего приложения, а номер позиции раскрывается в локальной карточке с точным якорем. Пользовательский PDF, включённый в третью вкладку, является пятистраничной обзорной памяткой, а не полным нормативным текстом с таблицами приложений; это прямо указано в интерфейсе. Для юридически точной проверки конкретной редакции нужно сверять действующий полный текст постановления.

## 4. Критерии приёмки

| № | Критерий | Техническое покрытие | Фактический статус
|---|---|---|
| 1 | Точность ≥85% на тестовом датасете из 20 товаров | Есть `backend/data/evaluation.json` (20 cases) и benchmark top-1 | **Не измерено здесь**: нужна запущенная модель и PostgreSQL/pgvector |
| 2 | Один запрос <5 секунд | Benchmark измеряет wall-clock HTTP request в warm state | **Не измерено здесь**: зависит от CPU/RAM и модели |
| 3 | 100 товаров <2 минут | Есть ограничение 100, batch embeddings и benchmark на 100 запросов | **Не измерено здесь**: нужен запуск API/worker на целевой машине |
| 4 | Обновление базы без передеплоя | `PUT /api/v1/catalog` заменяет данные транзакционно; startup seeding теперь заполняет только пустую базу и не затирает API-обновления | Реализовано в коде; нужен интеграционный restart test |
| 5 | Уверенность по каждому товару | Confidence возвращается для каждого результата и отображается в одиночном/пакетном режиме | Реализовано; это оценка сходства, не юридическая вероятность |
| 6 | Ссылка на пункт постановления в каждом результате | Локальная ссылка с уникальным якорем на карточку (приложение + позиция) и внешняя ссылка на приложение | Реализовано в SPA; внешняя правовая страница открывается на уровне приложения, не гарантирует индивидуальный URL-якорь у стороннего сайта |
| 7 | Запуск через `docker-compose up --build` | Все сервисы и общие тома заданы в Compose | Конфигурация подготовлена; реальный запуск не проверен здесь |

## 5. Исправление npm-сбоя при Docker build

В предоставленном логе ошибка возникает на `RUN npm ci --legacy-peer-deps` в `frontend.Dockerfile` и заканчивается `npm error Exit handler never called!`. В проекте использовался `node:22-alpine`. Такая комбинация Node 22/24 + Alpine описана в npm/cli issue #8974 с практически идентичным логом и длительностью около 81 секунды. Для frontend build stage заменён базовый образ на `node:22-bookworm-slim`; то же изменение внесено в дополнительный root `Dockerfile`. Также добавлен `.npmrc` с публичным registry и сетевыми retry-настройками, а 125 tarball URL в lock-файле переведены с домена зеркала на `registry.npmjs.org` с сохранением integrity-хэшей.

Это устраняет найденную в конфигурации причину/условие воспроизведения, но Docker build на машине участника необходимо повторить, поскольку Docker daemon в проверочной среде отсутствует.

## 7. Повторяемая приёмочная проверка на целевой машине

1. Выполнить `docker compose up --build -d` и дождаться `GET /api/v1/ready` со статусом 200.
2. В интерфейсе открыть третью вкладку, загрузить searchable PDF на 60+ страниц, дождаться `completed`, проверить page_count и скачать TXT.
3. Выполнить `python scripts/benchmark.py --output benchmark-report.json`. Скрипт завершится с кодом 1, если точность <85%, одиночный запрос ≥5 секунд или 100 товаров ≥120 секунд.
4. Загрузить новый JSON через «Справочник», проверить новую версию в `GET /api/v1/catalog/status`, перезапустить контейнеры без удаления volumes и убедиться, что новая версия сохраняется.
5. Проверить переход из результата в третью вкладку на desktop и mobile: хэш должен содержать правильные приложение и позицию, целевая строка подсвечивается.

## 8. Остаточные ограничения, которые важно не скрывать

- OCR для сканированных изображений в PDF не реализован; поддерживается извлечение текстового слоя.
- Целевые показатели 85% / 5 секунд / 2 минуты требуют реального запуска benchmark и не могут быть гарантированы только изменением исходного кода.
- Обновление справочника сохраняется в PostgreSQL; встроенный JSON является seed только для пустой базы.
- Внешние ссылки ведут на страницу приложения в правовой системе; точный локальный deep-link по позиции реализован в самой SPA.
- Добавленный PDF — обзорная памятка пользователя на 5 страниц, не официальный полный текст постановления.


## Дополнительная стабилизация запуска (для устранения 502 при старте)

- Web теперь ожидает `service_healthy` у API, а не только факт запуска контейнера.
- API получает healthcheck по `/api/v1/ready` с окном запуска 240 секунд: это учитывает инициализацию модели и начальную индексацию каталога.
- Frontend повторяет проверку API каждые 5 секунд и показывает отдельное состояние «API недоступен», вместо бесконечного «Подключение…».
- Nginx передаёт исходный URI `/api/...` без переписывания префикса.

Эти изменения закрывают гонку старта сервисов и дают понятную диагностику, но если API завершается с ошибкой, для установления первопричины всё ещё нужны логи `docker-compose logs api`.

## Развёртывание с персональным `.env` проверяющего

Проверяющий создаёт `.env` из `.env.example`. Значения `POSTGRES_USER`, `POSTGRES_PASSWORD` и `POSTGRES_DB` обязательны в Docker Compose и передаются одинаково в PostgreSQL, API и Celery Worker. API формирует SQLAlchemy URL через `URL.create`, корректно обрабатывая специальные символы в пароле. На первом запуске с новым Docker volume PostgreSQL создаёт пользователя и базу по этим значениям. Сценарий `fix-db-password.ps1` оставлен только для разработчика, если он меняет пароль в уже существующем volume; проверяющим на чистом развёртывании он не нужен.
